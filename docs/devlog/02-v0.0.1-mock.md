# Sí, Mocking Data. No es broma.

> **Concepto histórico**
> Al comenzar el diseño visual del proyecto, comencé por la UI. Ya sabía que quería usar WebView2 y sabía qué estilo de diseño quería, pero obtener los datos de Rainmeter no era mi prioridad en ese momento. De esa forma, decidí comenzar a utilizar datos 'estáticos' o 'mocks' para simular los sensores.

## 1. Fundamentos y limitaciones de los mocks estáticos:

> En resumen, el problema principal fue la integración de `alert-helper.js`. Claramente, necesitaba dinamismo. No podía estar editando el código estático cada vez que quería probar algo, necesitaba una forma de simular los datos de forma 'real'.

Aquí me encontré con el siguiente concepto. Para iterar el frontend (HTML/CSS/JS) necesitaba probar cosas como:

- ¿Qué pasa si el disco llega al 100% de uso? ¿Cambia a color rojo?
- ¿Cómo se estira el gráfico de la GPU cuando hay un pico repentino de frecuencia?
- ¿Se comporta bien el _WeakMap_ del Heartbeat bajo estrés constante?
- ¿Cómo se comporta el sistema de alertas cuando hay un pico repentino de temperatura?
- ¿La UI se rompe si hay muchos cambios en el DOM?

## 2. Mocking de simulación (Random Walk):

> En resumidas cuentas, la idea era simular los datos de forma orgánica, no solo tirar números al azar, sino que tuvieran sentido. (Aunque claro, aún falta mejorar la coherencia).

En lugar de utilizar datos estáticos a través de un `.json` o 'configuración' (hardcoded), decidí crear un pequeño ¿Motor? de simulación basado en 'Random Walk', utilizando una función generadora llamada `Series`.

Esta clase replica el movimiento de la bolsa de valores (Random Walk), sumando o restando un 'step' a un valor base, limitado por un 'clamp' (mínimo y máximo).

```javascript
// La esencia del generador de picos orgánicos
function Series(init, min, max, step, opts) {
  /* ... */
}
Series.prototype.next = function () {
  this.value = clamp(
    this.value + rnd(-this.step, this.step),
    this.min,
    this.max,
  );
  // Simulación de picos cercanos al límite para probar el sistema de Alertas UI
  if (spikeChance > 0 && Math.random() < spikeChance) {
    this.value = clamp(this.max * ratio, this.min, this.max);
  }
  return this.value;
};
```

## 3. Comportamiento matemático correlacionado (Falso realismo):

> En esencia, me gusta complicar las cosas, así que decidí que los datos 'debían tener sentido termodinámico y de hardware'.

Por ejemplo, la temperatura de la CPU no sube de la nada. Si el uso (`cpuUsage`) sube, el reloj (`clock`) debería escalar en consecuencia, así como la temperatura (`tempC`) es el resultado de la temperatura ambiente más multiplicadores algorítmicos basados en el uso actual.

```javascript
// Fragmento real de mock-data.js simulando un Ryzen 7
var u = cpuUsage.next();
var f = easeUsage(u);
var clock = clamp(
  baseClock + (boostClock - baseClock) * f + rnd(-0.05, 0.05),
  baseClock,
  boostClock,
);
var t = clamp(
  ambient + 0.45 * u + 4 * (clock - baseClock) + rnd(-1.5, 1.5),
  30,
  95,
);
```

## 4. Comportamiento 'real' esperado:

En resumen, el comportamiento actual en la v0.0.1 > v0.0.2 es 'casi' real, simulando de forma constante y directa comportamientos rítmicos de hardware. Aunque claro, cada uno de estos valores están 'aislados' entre sí (el uso de la GPU no afecta a la CPU de forma directa). ¿Esto es necesario añadirlo en versiones futuras? Posiblemente no. ¿Lo haré? Posiblemente sí, porque como dije: 'Me gusta complicarme las cosas'.

## Conclusión:

Gracias a este ¿motor? de `mocks`, pude aislar por completo la capa visual, probar las gráficas de forma aislada, el comportamiento de los 'hover', simular casos 'reales' de estrés y comprobar el rendimiento de `Heartbeat`. Cuando este último simplemente busca etiquetas HTML por sus selectores `[data-field]` e inyecta los valores, al motor gráfico no le interesa de dónde vienen los datos, solo resuelve las peticiones de los bundles de forma organizada para renderizar en el DOM sin necesidad de estresar mi hardware real. Sí, todo esto nació por esa simple razón.

> **Nota**: Esta abstracción me permitió además aislar el código para ejecutarlo en un navegador web corriente y poder probarlo de forma Local (sin necesidad de encapsularlo en Rainmeter y Windows todo el tiempo), lo cual fue una ventaja enorme a la hora de trabajar con herramientas de inspección de DOM y agentes de IA.
