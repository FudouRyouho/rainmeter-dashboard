# Comienzos del proyecto

> **Resumen general**
> Este proyecto inició como un desafío personal o un juego para mí, en el cual quería retarme a mí mismo a crear una integración limpia entre Rainmeter y WebView2 usando únicamente HTML/CSS y Vanilla JS. El objetivo era que sea funcional, no perfecto, pero sí limpio y eficiente.

## 1. Primeros pasos: El plugin `PluginWebView` (escrito por _khanhas_).

Cuando encontré este plugin, me motivé a hacer algo con él. Comencé el proyecto utilizando mocks para simular datos de la API de Rainmeter, ya que no sabía muy bien cómo este funcionaba, pero al investigar un poco más y terminar la 'ui' inicial, noté errores en la comunicación entre Rainmeter y el plugin. El plugin no funcionaba. Al no encontrar mucha información al respecto y ver que el proyecto llevaba mucho tiempo sin ser actualizado, decidí investigar el source por mi cuenta. Allí fue cuando descubrí que el plugin estaba roto al acceder a los datos en los punteros de memoria. Con ayuda de la IA, se realizó un fork local y personal para 'arreglar' el plugin. Hoy en día, ese fork es el que se utiliza en el proyecto. Un pendiente en el futuro es realizar el fork como corresponde para subir los cambios al repositorio de forma correcta, así como verificar si existen otros problemas en el plugin.

## 2. Maduración de la UI: ¿Por qué SVG nativo?

Cuando comencé a 'idealizar' o 'visualizar' cómo mostrar gráficas en el proyecto, pensé en utilizar librerías. Pero los principios de cómo 'empezó' el proyecto, así como el posible 'overhead' de utilizar librerías, me hizo pensar: ¿Cómo puedo dibujar gráficas en tiempo real en la UI de forma eficiente? ¿Realmente necesito una librería para esto? ¿Cómo lo hacen este tipo de librerías?

Ahí la decisión fue clara. Con un poco de investigación y planteos con la IA, llegamos a la conclusión de que teníamos algo interesante por delante.

> ¡Los SVG, en esencia, son matemáticas!

Sabiendo esto, comencé a hacer mi análisis en base a las siguientes razones:

- **Baja Latencia:** Dibujar gráficos vectoriales mediante la formación directa de la etiqueta path (`d="M0,56 L50..."`) reduce la complejidad de la renderización en el navegador a simples matemáticas.
- **Precisión controlada:** Al usar JavaScript Vanilla (ej. `setPathD`), las dimensiones (con sus _paddings_ y normalizaciones algorítmicas o logarítmicas) responden de manera predecible, lo que da como resultado un mayor control visual.
- **Mantenimiento Cero:** La implementación iba a ser 'costosa' inicialmente con funciones de matemática pura (como `ringMax`, `toPathFromRing`), pero a futuro ya tenía todo lo necesario para escalar con lo mínimo que necesite. Bajo este concepto, tener el control total sobre las utilidades fue una decisión que me dio mucha satisfacción.

## 3. ¿En serio? ¿Por qué no usar librerías como React?

Cuando empecé este proyecto, me planteé hacerlo de forma 'nativa', sin librerías, para comprender los fundamentos de "cómo el DOM se rompe con múltiples mutaciones". Esto, muchos frameworks (o al menos los que yo uso), lo manejan con virtualización. Pero a nivel 'práctico', esta virtualización no es más que "duplicar objetos en memoria", validar las mutaciones en cada tick, recalcular y finalmente aplicar los cambios en el DOM. Esto me parecía un 'overhead' innecesario para lo que quería lograr, además de que el objetivo era tener el "menor consumo posible". No recuerdo precisamente cómo llegué a este punto, pero me planteé: ¿Y si genero un 'caché' del DOM en memoria, y solo actualizo los valores que necesito?

1. **Headless UI `data-` mi primera inspiración**: Manipulando el DOM de forma directa con el uso de (`data-field`) o del _TextNode_ del DOM (`el.textContent = value;`) evito causar un recálculo en el árbol de diseño.
2. **Buffer circular**: Modificamos el 'Caché' de dimensiones para evitar la sobrecarga de renderización utilizando un `WeakMap` y matrices circulares (`push(ring) % length`). Así evitamos el recálculo del array completo con `getBoundingClientRect()`.

## 4. Mi sueño frustrado "Crear un juego": El patrón Heartbeat (tick loop)

Al tener gran parte de la UI trabajando con mock data generando valores 'casi reales', comencé a notar picos de memoria de entre 120-160 MB de RAM. Lo cual es muy poco, pero ¿Podría ser menos no? Investigando y viendo la estructura del proyecto comencé a preguntarme: ¿El DOM se está sobrecargando? ¿La actualización de los datos está colisionando con la actualización del DOM? ¿Debo implementar async/await de alguna forma para separar los procesos?

> La respuesta es no, no es necesario, al menos no en este caso. La clave está en que los 'procesos' estén ordenados de forma eficiente.

- **`HeartbeatInstance`**: La idea es simple, centralizar la lógica de actualización de datos en un solo lugar para evitar colisiones entre procesos. Cada 'bundle' se suscribe a 3 fases ordenadas por ciclo de actualización:
  - `measure`: Exclusivo para leer los datos del puente de C# de manera segura.
  - `compute`: Exclusivo para matemáticas, promedios y push a los anillos en memoria.
  - `render`: Exclusivo para pintar/escribir en el DOM (`setPathD` y `setField`).

Al separar estrictamente las fases de lectura (measure) y escritura en DOM (render), WebView2 nunca tiene que recalcular los estilos a mitad de un proceso. Esto bajó el consumo a apenas 65MB y garantizó ciclos ultra-responsivos.
